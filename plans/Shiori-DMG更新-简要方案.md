# Shiori 统一 DMG 应用内更新：简要方案

日期：2026-09-13。状态：`v0.2.1/build 3` 已发布，GitHub Pages 更新清单与公开 DMG 已完成公网校验；本机已安装 `v0.2.0/build 2` 过渡版，等待维护者亲自点击更新完成生产链路验收。

## 要实现的效果

用户安装包含更新功能的 Shiori 后，可以在 App 内完成后续升级：

**检查更新 → 查看版本说明 → 点击安装 → 下载并验证 → 退出、替换并重启 → 使用新版。**

正常流程无需打开 GitHub、手动打开 DMG、删除旧 App 或拖拽替换。升级保留游戏配置和用户数据；相关游戏或 Wine Steam 正在运行时暂缓安装，由用户自行保存并退出。

## 已确定的选择

| 项目 | 决定 |
| --- | --- |
| 安装包 | 统一使用 `Shiori-版本号.dmg`，首次安装和应用内更新下载同一个文件 |
| 更新组件 | 沿用项目已接入的 Sparkle 2 |
| 文件托管 | GitHub Releases 存放 DMG，GitHub Pages 提供更新清单 |
| Apple 开发者账号 | 本阶段不要求购买；继续使用 ad-hoc 应用签名 |
| 更新包验证 | 使用独立的 Ed25519 密钥签署最终 DMG，客户端验证后才安装 |
| 更新方式 | 默认每日检查并提示，由用户点击安装，不静默强制升级 |
| 本阶段范围 | 完整 DMG 更新；增量更新、正式公证和重做更新界面留作后续 |

Sparkle 支持直接用 DMG 更新普通 App，因此不需要让用户选择 DMG 或 ZIP。[官方说明](https://sparkle-project.org/documentation/)

## 发布新版本时，你需要做什么

已提供统一发布入口。维护者填写新版本号和变更说明后，工具依次构建、生成 DMG、签署更新、校验并准备发布。

正式发布的顺序必须是：**先上传并验证 DMG 可下载，再上线对应更新清单。** 只上传 GitHub Release 的 DMG 不会自动通知客户端；清单必须同步维护。用户不需要接触清单、签名或校验文件。

首次配置需要启用 GitHub Pages，并保管、备份更新签名私钥。此后每次发布复用同一套配置。私钥不能放进源码仓库、App 或 Release。

## 体验边界

- 不含更新功能的旧版本需要最后一次手动安装过渡版；通常退出后直接拖入并选择“替换”，无需提前删除旧 App。
- 没有 Apple Developer ID 与公证，首次安装可能需要用户在系统安全设置中允许。后续启动或权限提示以真实测试为准，不能承诺所有机器都没有系统提示。[Apple 说明](https://developer.apple.com/developer-id/)
- 网络不可达、磁盘空间不足或目录权限受限时，更新应给出可理解的提示，不能提前删除旧 App；断电等异常后的恢复能力必须通过测试界定。
- 前一候选 DMG 为 484558775 bytes（约 462.1 MiB）；配置持久化修复后必须重新构建，最终大小以新产物为准。每次更新仍为全量下载，速度取决于用户到 GitHub 的网络状况。
- 更新私钥遗失会影响老用户继续接收更新；当前没有 Developer ID 作为备用信任路径，必须认真备份。[Sparkle 密钥说明](https://sparkle-project.org/documentation/#rotating-signing-keys)

## 完成标准

在真实安装的旧版上点击“检查更新”，不打开浏览器即可从 GitHub 下载 DMG，完成校验、替换和重启；再次检查显示已是最新版；原有游戏配置、Prefix 和样例存档正常，相关游戏仍可启动。

同时验证下载失败、签名错误、游戏运行、权限不足等场景。只有构建成功或出现更新提示，均不算完成。
